# Critique of `report/04-design.md` (`pyview.forms` draft)

Scope: draft 04 (+05 examples, 06 roadmap, 07 evidence) checked against the research corpus, the spike (`proto/`, re-run: `ALL OK`), pyview's code, and the alternative design (`synthesis/alt_design_changeset.md`). Paths are relative to the scratchpad unless absolute.

## 1. Contradictions

1. **Ibis filter arguments cannot carry the option dicts/lists the ladder is built on.** Draft 4.3/4.7/5.3/5.5 write `input({"type": "email", "placeholder": "…", "class": "w-full"})`, `render(["name", "email"])`, `input({"options": roles})`, `field({"widget": "radio", "labels": {...}})`, `render(steps[step])`. pyview's vendored Ibis splits filter args on commas with `utils.splitc` (respects quotes, **not** braces/brackets) and then `ast.literal_eval`s each piece (`/home/user/pyview/pyview/vendor/ibis/nodes.py` L86-95). Run today: `{{ x | input({"type": "email", "class": "w-full"}) }}` → `TemplateSyntaxError: Unparsable argument '{"type": "email"'`; `render(["name", "email"])` → same; `input({"options": roles})` → "Arguments must be valid Python literals". Only single-key dicts and scalar literals work. 06-roadmap ("keyword-style options need a dict literal — acceptable for level 1–2") understates this: levels 1–2 and examples 5.3/5.5 do not parse. Fix: either a custom `{% input form.email type="email" class="…" %}` tag in phase 2 (not "deferred"), or a patch to `splitc` to track bracket depth, or a `form.email.input("type=email", "class=w-full")`-style string-args convention. Decide before writing docs.
2. **Gating rule text vs. spike semantics.** 4.6: `visible(field) = action is not None and (action == "submit" or field.path (or a prefix/child of it) ∈ used)`. "a prefix of it ∈ used" means a field is visible when an *ancestor* is used, which is the opposite of the spike (`pyview_forms_proto.py` `visible_errors`: visible when a used path has the field as prefix; "children never inherit used-ness from a parent or list", 07 last paragraph). Under the 4.6 wording, clicking *Add address* (which marks `("addresses",)` used) would reveal `missing` on every blank row — exactly what 07 shows must not happen. Rewrite the formula: `visible ⇔ action == "submit" or ∃u ∈ used: u[:len(path)] == path`.
3. **`_target` for `[]` names decodes to a path that never matches.** 4.5 says `_target` "is decoded into a path tuple the same way". Spike output (`test_proto.py`): `_target=user[tags][]` → `('user', 'tags', '')`. `used` then holds `("tags", "")` and `errors_for(("tags",))` stays hidden forever for multi-selects/checkbox groups. The decoder must strip the trailing `""` segment for `_target` (Phoenix does).
4. **`_unused_*` stripping is specified for the wrong wire shape.** 4.5 lists `_unused_*` among top-level meta keys and claims the 1.x switch is "one line". `phoenix_client_js.md` (authoritative): the prefix goes on the *last* segment — `user[_unused_name]`, `user[addresses][0][_unused_city]`, `user[_unused_tags][]`. The spike's only test of this is `_unused_user[name]=` (`test_proto.py`), a shape the client never sends; `decode_form` only checks `key.startswith("_unused_")`. So the upgrade path is unverified and, as written, would inject `_unused_name: ""` keys into `params` and pydantic (harmless with `extra="ignore"`, an `extra_forbidden` error otherwise).
5. **`phx-feedback-for` on error containers contradicts the corpus.** 4.6/4.7 emit `phx-feedback-for` "so client-side hiding still applies during form recovery". `phoenix_client_js.md` Lessons/Avoid #8: "Don't reintroduce a `phx-feedback-for`-style client class toggle… the 0.20.17 mechanics need exact-name matching that breaks on renamed dynamic rows"; `pain_points_praise.md`, `ecto_changeset.md` say the same. Concretely: (a) the server already renders an error only when its path is used, so on recovery there is nothing to hide; (b) the client re-adds `phx-no-feedback` after *every* patch to containers whose input has no `PHX_HAS_FOCUSED` — a list-level error rendered after an *intent* (`_target` is the button, no input was focused) or after `form.add_error(...)` from a check would be marked `phx-no-feedback` even though the server decided it is visible; (c) with the default unstyled theme nothing defines `.phx-no-feedback`, so the attribute is either inert or harmful. Drop it; handle recovery explicitly (see §5).
6. **Hidden-by-rule fields "dropped before validation … so a hidden required field cannot block submission" (4.7) is false and contradicts the research.** Dropping a required field's value yields `missing`, which blocks submission. `nested_dynamic_patterns.md` "Declarative visibility": "Hidden ≠ deleted: keep the params… pydantic has no 'ignore this field' switch — use the union/variant model for real conditional requiredness"; 06-roadmap's own risk note says "if you hide it, keep a hidden input". The alt design (§10.3) makes the same point.
7. **Golden-path `<form>` has no `id`, so form recovery never runs.** 4.2 and 5.2 write `<form phx-change="validate" phx-submit="save">`. `phoenix_client_js.md`: recovery collects only `form[phx-change]` elements **that have an `id`** (v0.20.17 `view.js` L1290-1300) and Lesson 5 says "always render a stable `id` on `phx-change` forms". The draft never mentions form ids, `phx-auto-recover`, or what the server does with the replayed change (`_target` = first input).
8. **Union "lossless switching (verified)" was verified against a payload the client cannot send.** `test_proto2.py` L69-71 removes the old variant's inputs and adds the new variant's before calling `validate`. In the browser the select's `phx-change` fires while the *old* fieldset is still in the DOM, so the payload is `{kind: "personal", company: "ACME"}` — the shelf entry for `personal` is polluted with `company`, `extra="forbid"` models get `extra_forbidden`, and the "values typed into the previously selected variant" path is exercised differently from what was tested. Works by accident with `extra="ignore"`; must be re-verified with the real ordering, or switch to variant-named inputs (§5).
9. **"Params replaced by each payload" (4.5) vs. the corpus and the draft's own examples.** `conform.md` Avoid: "Keep the accumulated params dict on the server and overlay each phx-change payload"; `ecto_changeset.md`: absent key ⇒ keep `data`. Draft 5.5 quietly introduces `Form(..., merge_params=True)` and `form.hidden_fields(exclude=…)`, neither in the 4.4 API. Edit forms (5.1) never say whether `data` is merged into the validation input; if not, any unrendered field (`id`, `created_at`, `last_watered` when omitted from the template) is `missing` on every change; if yes, `"" → absent` means clearing a field silently restores the old value (the alt design's §10.4 point).
10. **Decoder "(verified)" claims exceed the spike.** 4.5/4.9: "`__proto__`/dunder segments rejected", "max 10 000 pairs", "list index ≤ 10 000". `pyview_forms_proto.py` has only `max_depth`; grep for dunder/pair limits is empty. Also `items[][name]` is accepted (`test_proto.py` line 5) although `ecto_changeset.md` says "refuse `a[][b]`" and Rack groups it differently — pick one and say so.
11. **"Errors from a plain `raise ValueError` keep loc `()`" (4.6)** is only true in `model_validator`s; in a `field_validator` the loc is the field (pydantic_core.md). Minor wording, but it decides whether a message shows inline or in the summary.

## 2. Major gaps (things the maintainer asked for that are missing or under-specified)

1. **What `payload` looks like after phase 0.** ws_handler today gives `parse_qs` dicts; `uploads.maybe_process_uploads` reads `qs["_target"][0]`; docs promise `payload["query"][0]`; `ChangeSet.apply` reads `payload["_target"][0]`. The draft says ws_handler "uses `decode_form`" and binding "gets nested access" without stating the new shape, whether `parse_qs` consumers keep working, or how the `Form` receives *both* the decoded dict and meta. The alt design's `Params` object (target, intents, meta, recovered) answers this; the draft has no equivalent.
2. **BYO HTML + gating + timing.** 4.7 "Escape hatch: hand-written HTML needs only `name`/`id`/`value`/`attrs`/`errors`". But `show_errors="blur"` is *implemented by the widgets* emitting `phx-debounce="blur"`; at level 3 the client pushes on every keystroke (no default debounce), so errors appear on the first character. Say whether `Field.attrs` includes `phx-debounce` (and `aria-*`), and document the level-3 contract for `phx-feedback-for` (answer: none, drop it).
3. **Passwords.** `SecretStr → password` widget + "attempted values always survive, `Field.value` reads params first" ⇒ the password is echoed back in `value="…"` on every re-render (and `data=` would serialise `**********`). Superforms/Conform have `hideFields`; the alt design writes `value=""`. Specify: password widgets never render a value; `Field.value` for `SecretStr` is `""`.
4. **Uploads (4.9 is three lines).** `live_file_input` renders `name="{config.name}"` (flat, outside the `as_` prefix); the upload manager looks up configs by that name via `_target`; the decoder would classify it as meta. A required `Annotated[list[UploadEntry], Upload(...)]` field never appears in params ⇒ `missing` on every change. `consume_uploads()` is async and belongs in the handler, not "in `submit()`". Needs a real section: naming under the prefix or not, how validation skips upload fields until submit, how entries reach `form.model`.
5. **Multiple forms, LiveComponents, `phx-target`.** Nothing on `id` per form (recovery, `phx-target={meta.myself}`), events routed to `Component.handle_event(event, payload, socket)`, or two `Form`s in one view. superforms lesson 10 and the client research both flag it.
6. **Dataclasses / TypedDict.** Brief: "as simple as passing a Pydantic class or dataclass". 4.4 accepts `TypeAdapter` but every introspection path (`model_fields`, `title`, `metadata`, discriminator) is `BaseModel`-only; the spike's `_unwrap_model` returns `None` for anything else. Either say "pydantic models only in v1" or specify introspection via `TypeAdapter.core_schema`.
7. **Recovery after reconnect.** The server's `used` set dies with the remount; the client replays one `phx-change` with stale values and `_target` = first input. Draft says nothing; the alt design (§5.3) has `phx-auto-recover="recover"` + `Params.recovered` ⇒ mark non-blank paths used. Adopt.
8. **Explicit intents in the handler.** Intents are applied silently inside `validate()`; the handler cannot refuse an add, move focus to the new row (4.7 promises "focus moves to the new row's first input" without a mechanism — `push_event` + a hook? `JS.focus` on what element?), announce it, or test what happened. Expose at least `form.last_intent` / `form.target`, or the alt's `params.intents` + `apply_intents()`.
9. **Name collisions between `Field`/`Form` attributes and model fields.** Ibis resolves `a.b` by `hasattr` first (`vendor/ibis/context.py` L75-94), so for `class Item(BaseModel): name: str` the template `{{ row.name }}` returns the HTML name string `profile[items][0][name]`, not the sub-field — silently. Same for model fields named `id`, `value`, `label`, `key`, `type`, `options`, `errors`, `required`, `hint`, `path`, `used` on nested models and `id`/`data`/`model`/`action`/`errors`/`valid`/`keys`/`rows`/`field` on the top-level form (`Form.__getattr__`). `name` and `id` are the two most common field names in any app. Fix: either a sub-namespace (`form.f.name`, `row.f.name`) or Django-style renamed attrs (`html_name`, `dom_id`, `html_value`) — decide now; it is the template contract.
10. **Ibis dotted list indices.** `{{ form.addresses.1.city.value }}` rendered empty in `exp3_ibis.py` (Ibis passes `"1"` as a string; proto1's `__getitem__` does not intify — proto2 does). 4.4 must state that `Field.__getitem__` accepts digit strings.
11. **Testing.** 4.10 uses `encode(...)` and 5.8 `encode(..., intent=...)`; neither is defined. Specify the alt's `wire(form, values, target=)` that emits exactly what the 0.20.17 client sends for the *rendered* inputs (incl. hidden `_key`, hidden `false`, submitter pair).
12. **Migration.** "`ChangeSet` becomes a thin wrapper" — but `ChangeSet.apply(payload)` takes the `parse_qs` dict incl. `_target`, `save()` takes `parse_qs` too, `attrs` returns *changes* (untouched fields render `""`), `errors` is `dict[str,str]`. Write the shim (the alt design §9 has one) and list the behavioural changes (blank values now arrive; model-level errors move to form level).
13. **Auto-routing (`Form(on_submit=)`).** Deferred, fine, but the open question is not analysed: t-strings still need `phx-change="{…}"` strings; `BaseEventHandler`/`AutoEventDispatch` dispatch by method name; components route by `cid`. Say what `form:registration:validate` would mean for each.
14. **`Input(...)` on models you do not own** and `model_config["form"]` are asserted without the side-car API (`Form(ui={...})`) that 06 recommends.

## 3. Minor issues

- 4.7 filter names `input`, `label`, `errors`, `field`, `render`, `debug` land in Ibis's single global `filtermap`; `field` also collides mentally with pydantic's `Field` and the draft's `Field` class. Consider `f_input`/`form_*` or a `form.` namespace like the existing `js.*` filters.
- `_target` is absent on submit and `"undefined"` in ≤1.0.5; 5.4 `form.target == ("country",)` needs the prefix stripped and a `None` case documented.
- 4.6 "Form-level errors show … when every field they name is used": a `()` error names no fields; define or delete.
- `forms.configure(...)` is process-global mutable state; say how it interacts with per-`Form` overrides and tests.
- `Field.value: Any` — should be `str | list[str]` (alt §10.9); `bool → "true"` serialisation must agree with the hidden-`false` checkbox trick.
- `Form.rows(path)` and `Field.__iter__` both exist; pick one.
- `EmailStr` requires `email-validator` (not installed in pyview's venv) — the golden path fails at import unless it is made an extra.
- 07's "~300-line spike" is ~540 lines across two files; 4.0 says "pydantic 2.13", fine.
- Intent value grammar `move:k7f3:up` vs 5.2 `intent_button("move:up", …)`: two encodings in one document.
- Dev-mode warnings "when an `id` collides" cannot see ids written in raw HTML.

## 4. DX walkthrough notes (mentally typed)

- **Level 0 (4.2, Ibis):** 12 lines Python + 4 HTML. Concepts: `Form`, `validate`, `submit`, `valid`, `model`, `payload: dict`, `{{ form | render }}`. Surprises: must remember `phx-disable-with` yourself; no form `id` (recovery off); on a valid submit nothing resets the form unless you `push_navigate`; `save` with invalid data silently re-renders (fine). Good.
- **Level 1:** `{{ form.password | field({"hint": "…"}) }}` works only because it is a single-key dict — the moment a user adds `"placeholder"` it is a syntax error at template compile (Contradiction 1). Not "a small local delta".
- **Level 2:** `{{ form.email | input({...3 keys...}) }}` does not parse. The whole level is unusable in Ibis as written.
- **Level 3:** works, but `phx-debounce` must be typed by hand and `form.name.attrs` renders `required` — pairs badly with GOV.UK `novalidate` unless the form tag adds it; `value="{{ form.email.value }}"` echoes passwords.
- **5.2 lists:** filters `key_input`, `intent_button` appear only here; the row `div` needs `id="{{ row.id }}"` by hand (forgetting it breaks focus/morph silently); `{{ row.primary | field }}` for a `bool` inside a row relies on the hidden-`false` trick emitting `profile[addresses][0][primary]=false` before the checkbox — fine.
- **5.3 union:** `{{ form.account.kind | field({"widget": "radio", "labels": {...}}) }}` fails to parse; `form.account.kind.value` is `""` before any change even though `Signup.account` defaults to `Personal()` — is the default's `kind` in `data`? Unstated (Field.value "then initial data" suggests yes, but `Form(Signup)` has no `data`; defaults need to be part of the value fallback).
- **5.4 dependent select:** `form.target`, `form.set` are not in 4.4; `Input(options=lambda form: …)` closure signature ("resolved with signature binding") is a new concept with two spellings.
- **5.5 wizard:** `render(steps[step])` cannot be expressed in Ibis; `hidden_fields`/`hidden_input` undefined; hidden inputs for a `list[Address]` of other steps means serialising nested rows to hidden inputs (not specified); `.step(paths)` returns a "proxy" whose relationship to the stored form is unclear. Concept count for one example: `submit`, `step`, `render(subset)`, `hidden_fields`, `merge_params` — five new ideas. The alt's one-model-per-step needs zero new API.
- **5.7 checks:** `async def unique_email(model, form)` on the constructor — I/O inside the form object; the handler-side `add_error` idiom is simpler and already in the draft. Keep one.
- Overall: the *core* (Form/validate/submit/Field) is a clean 7-concept API; the ladder above it invents ~15 more names across 4.7/5.x, several undefined, and the Ibis half of it does not compile.

## 5. What to adopt from the alternative design

Adopt:
1. **`Params` as a first-class decoded object** (`target: Path|None`, `intents`, `meta`, `recovered`) produced in `ws_handler` and injectable by type through `pyview.binding`. Resolves Major gaps 1, 7, 8 and keeps `parse_qs` consumers alive during migration.
2. **Ecto cast/merge semantics**: absent key keeps `data`; `""` becomes default/`None` and *is* a change; optional `permitted=` list. Fixes edit forms and Contradiction 9 without `merge_params`/hidden-field hacks.
3. **Variant-named union inputs** (`profile[account][business][company]`): loc→name is 1:1, no tag skipping, both variants coexist in params, no shelf, no cross-pollution (Contradiction 8). Keep the shelf only as an implementation detail if same-named inputs are still wanted.
4. **Explicit recovery**: `phx-auto-recover="recover"` + `Params.recovered` ⇒ mark non-blank paths used; delete `phx-feedback-for`.
5. **Explicit intents**: decode into `params.intents`, `form.apply_intents()` (or auto-apply but record `form.applied_intents` and expose `last_added_id`).
6. **`Field.value: str | list[str]` + `Field.typed`**, never echo `SecretStr`.
7. **`wire(form, values, target=)` test helper** that serialises the *rendered* inputs incl. `_key`, hidden `false`, submitter pair.
8. **`Ok(model) | Err(form)` from `submit()`** as an *additional* return shape (keeps "cannot forget the action" without making `match` mandatory).
9. **Copyable `components.py`** shipped alongside — the Phoenix stance — so the widget registry/theme is optional and the "customization wall" has a documented exit.

Do not adopt: dropping auto-render from the core (the maintainer's stated goal is "here's my pydantic class, do the rest"; keep `render` but ship it as the thin layer over `Field`), form-context validators as v1 core (`validate_confirmation`/`validate_acceptance` are nice but pydantic idioms in 4.6 already cover them; add later), schemaless `types=` (nice-to-have, v2), and renaming back to `Changeset` — one object is right for pyview, but keep the *cast/validate/action* vocabulary in docs since it "resonated".

## 6. Verdict and the 5 most important fixes

**Verdict:** The data layer (bracket decoder, `parse_qsl(keep_blank_values=True)`, whole-model validation, `(path, code, params, message)` errors with a human catalog, used+action gating, row keys, `JS.dispatch("change")` intents) is sound, matches the corpus, and mostly runs in the spike. The rendering ladder is not implementable in Ibis as written, several "verified" claims are verified against the wrong payloads, and the draft is silent on the boring but decisive integration facts (payload shape after phase 0, form ids/recovery, uploads, passwords, edit-form merge). Ship phases 0–1 from this draft after the fixes below; re-RFC phase 2 (Ibis syntax, naming contract) before coding it.

**Five fixes, in order:**
1. **Fix the Ibis option syntax before designing the ladder around it**: add an `{% input %}`/`{% field %}` tag (or bracket-aware `splitc`) in phase 2 and rewrite every 4.3/4.7/5.x example so it parses; drop `render([...])`/`input({"options": var})` forms or give them tag equivalents.
2. **Resolve the template naming contract**: `Field`/`Form` attributes must not shadow model field names in Ibis's `hasattr`-first resolution — introduce `form.f.<name>` / `row.f.<name>` (or rename to `html_name`/`dom_id`/…) and make digit-string indices work.
3. **Specify the wire→handler contract**: a `Params` object with `target` (trailing `[]` stripped), `intents`, `meta` (both 0.20.17 tail and 1.x `meta`/last-segment `_unused_`), `recovered`; state exactly what `payload` is after phase 0 and how uploads/`ChangeSet`/binding keep working.
4. **Adopt Ecto merge semantics** (absent keeps `data`, `""` is a change to default/`None`, optional `permitted`) and delete `merge_params`/`hidden_fields`; document edit forms and wizards on top of it; never echo `SecretStr`.
5. **Correct the gating/recovery story**: rewrite the `visible()` formula to the spike's ancestor-of-used rule, remove `phx-feedback-for`, require a form `id`, add `phx-auto-recover` handling, and re-verify the union switch with the real client ordering (or move to variant-named inputs).
