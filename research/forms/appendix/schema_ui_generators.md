# Schema-driven UI generators and fluent form builders: RJSF, JSON Forms, FormKit, Filament + Livewire — the schema / ui-schema / widget-registry / theme layering

Versions researched (from cloned GitHub main branches, 2026-09-12): react-jsonschema-form `@rjsf/core` 6.10.0; JSON Forms `@jsonforms/core` 3.9.0-alpha.1; FormKit monorepo (`@formkit/core` package.json says 2.1.2 on master); Filament `4.x` branch (v3 API names differ slightly — noted where relevant); Livewire `4.x` branch (v3 `wire:model` semantics largely retained via `.lazy`).

## TL;DR

- All four systems converge on the same **four-layer split**: (1) *data schema* (what: types, constraints), (2) *UI schema* (how: widget choice, order, layout, visibility rules), (3) *widget/renderer registry* (which component renders a given schema+ui node, looked up by name or by tester rank), (4) *theme/templates/classes* (the HTML skeleton and CSS classes around each widget). pyview should make the same cuts, with Pydantic as layer 1.
- RJSF derives everything from a JSON Schema and an optional `uiSchema` mirroring the data tree; ids are path-derived (`root_tasks_0_title`, configurable `idPrefix`/`idSeparator`) and HTML `name`s are pluggable (`bracketNameGenerator` -> `root[tasks][0][title]`), which is exactly the shape Phoenix's client already sends.
- JSON Forms separates *data schema* from a *layout tree* of `Control{scope:'#/properties/x'}` elements with `rule: {effect: SHOW|HIDE|ENABLE|DISABLE|READONLY|WRITABLE, condition}` and dispatches renderers by `rankWith(n, tester)` — the cleanest "auto UI, but overridable per node" design.
- FormKit's string rule DSL (`validation="required|length:3,10|email"`, hints `*` force, `+` run-on-empty, `?` non-blocking, `(300)` debounce) plus `validation-visibility: live|blur|dirty|submit` is the best ergonomic model for "when do I show this error"; server errors merge in via `errors` (form-level) and `input-errors` (per-path map).
- Filament's fluent PHP DSL (`TextInput::make('email')->email()->required()->live(onBlur: true)->hidden(fn (Get $get) => ! $get('is_company'))`) with name-based utility injection (`$state`, `$get`, `$set`, `$record`, `$operation`) is the most "here is my model, do the rest" DX and maps naturally onto Python closures + signature-driven binding pyview already has.
- Livewire keeps form state as plain nested properties bound with `wire:model="items.0.name"` (dot or bracket paths), per-property validation on `.live`/`.blur` round-trips, and a `Form` object with `#[Validate('required|min:5')]` attributes — the closest analogue to "pydantic class + changeset".
- Where schema-driven UIs fall down: layout (JSON Schema has no rows/columns), bespoke UX (custom widgets end up re-implementing the framework), generic look, and the "escape hatch cliff" (once you need one custom field you often abandon the generator). Every project above added a second schema or a template registry to compensate.

## Mental model & core abstractions

**RJSF** (`<Form schema uiSchema formData validator ... />`). `schema` is JSON Schema; `uiSchema` is an object literal *following the same tree* as the data, with `ui:*` keys (or equivalently `ui:options: {...}`). Rendering walks the schema: `SchemaField` picks a *Field* (object/array/string/number/boolean/multi-schema) from `registry.fields`, the field picks a *Widget* from `registry.widgets` (`ui:widget: 'textarea'` etc.), and each level is wrapped in a *Template* from `registry.templates`. `Form` requires a `validator` (`@rjsf/validator-ajv8`) — validation is a pluggable interface, not built in. Themes are `withTheme({widgets, fields, templates, ...formProps})` — the theme object has the same shape as Form props and is *merged* over defaults (docs: "providing a single widget in widgets will merge this widget with all the default widgets ... but overrides the default if the theme's widget's name matches"). Published themes: `@rjsf/mui`, `@rjsf/antd`, `@rjsf/chakra-ui`, `@rjsf/fluentui-rc`, `@rjsf/semantic-ui`, `@rjsf/bootstrap-4`, `@rjsf/shadcn` (unverified exact list in 6.x).

**JSON Forms** (`<JsonForms schema uischema data renderers cells validationMode additionalErrors i18n onChange />`). Two documents: the JSON Schema and a *UI schema* that is a **layout tree**, not a mirror of the data. Element kinds (packages/core/src/models/uischema.ts): `Layout` (`VerticalLayout`, `HorizontalLayout`, `Group`), `Categorization` (tabs/steps), and `ControlElement { type: 'Control'; scope: '#/properties/name'; label?; options? }` binding to a JSON-pointer. Any element may carry `rule: { effect: RuleEffect; condition }`. Renderer selection: each renderer exports a `RankedTester = rankWith(rank, tester)`; the framework runs all testers for a node and uses the highest rank (`NOT_APPLICABLE = -1`). Testers compose: `and(uiTypeIs('Control'), schemaTypeIs('string'))`, `scopeEndsWith('name')`, `optionIs('multi', true)`, `formatIs('date')`, `isEnumControl`, `isObjectArrayControl`. Cells are the same idea one level down (the raw input inside a control). If no `uischema` is passed, one is generated from the schema (a `VerticalLayout` of Controls).

**FormKit** (Vue). One `<FormKit type="text" name="email" validation="required|email" />` component for every input; `type="form"`, `group`, `list` are structural nodes that make the value tree nested. Under the hood everything is a `FormKitNode` tree (`@formkit/core`) with `node.value`, `node.store` (messages), `node.setErrors(localErrors, childErrors)`, `node.clearErrors()`. Inputs are defined as *schemas of sections*: `outer(wrapper(label(), inner(prefix(), textInput(), suffix())), help(), messages(message('$message.value')))` — each `createSection('outer', () => ({$el:'div', attrs:{'data-type':'$type', ...}}))` is a named slot whose class is computed by `rootClasses(sectionKey, node)` (default `{ ['formkit-' + kebab(key)]: true }`) then overlaid by the `classes` config/prop and `<section>-class` props. `FormKitSchema` is a JSON DSL for whole forms: nodes are `{$el:'div'}`, `{$cmp:'FormKit', props:{...}}` or `{$formkit:'text', ...}` sugar, with `if/then/else`, `for`, and `$get(id).value` expressions.

**Filament + Livewire** (PHP). Filament is a *fluent object DSL*: components (`TextInput`, `Select`, `Repeater`, `Builder`, `Section`, `Wizard`...) are instantiated with `X::make('name')` and configured by chained methods; almost every method accepts either a value or a closure whose parameters are injected by name (`$state`, `$rawState`, `$get`, `$set`, `$record`, `$operation`, `$livewire`, `$component`). The schema array lives inside a Livewire component whose public `$data` array is the form state; Livewire syncs it with `wire:model` on round-trips, and re-renders the schema server-side (in v4 optionally partially via `->partiallyRenderComponentsAfterStateUpdated(['email'])` or with zero round trip via `->hiddenJs('$get("is_company")')` / `->afterStateUpdatedJs(...)`). Livewire itself: `public PostForm $form;` where `class PostForm extends Form { #[Validate('required|min:5')] public $title = ''; }`, template `<input wire:model="form.title">`, `@error('form.title') {{ $message }} @enderror`.

## Data in (naming, parsing, coercion, nested/lists)

- **RJSF** stores `formData` as a JS tree; ids are `idPrefix` + `idSeparator` joined path (`root_tasks_0_title`), and `name` = id unless `nameGenerator={bracketNameGenerator}` (`root[tasks][0][title]`, auto-appends `[]` for multi-value) or `dotNotationNameGenerator` (`root.tasks.0.title`). Custom `NameGeneratorFunction(path: string[], idPrefix, isMultiValue?)`. Coercion is widget-driven (number widgets emit numbers); empty text -> `undefined`, stored as `null`; `ui:emptyValue` overrides. `omitExtraData` + `liveOmit: 'onChange'|'onBlur'` strip data not covered by the schema (important when a `oneOf` branch changes). `experimental_defaultFormStateBehavior` controls how `default`s are merged into `formData` (`arrayMinItems`, `emptyObjectFields`, `constAsDefaults`, `mergeDefaultsIntoFormData`).
- **JSON Forms** stores `data` as a tree; every `Control.scope` is a JSON pointer into the *schema*, and the data path is derived from it (`#/properties/address/properties/city` -> `address.city`). Arrays render via `isObjectArrayControl`/`isPrimitiveArrayControl` renderers with add/remove and optional sort.
- **FormKit** builds the value tree from `name`s: `<FormKit type="group" name="address"><FormKit name="city"/></FormKit>` -> `{address:{city}}`; `type="list"` yields arrays; the `repeater` (in `@formkit/addons`) adds/removes list items. Casting is per input type (`number` input has `number="integer|float"` prop; unverified exact name).
- **Livewire** binds DOM to nested PHP properties: `wire:model="address.city"`, `wire:model="items.0.name"`, bracket form `items[0].name` also allowed. Modifiers `.number` / `.boolean` cast on the server (v4 docs table). Checkboxes bound to an array property produce a list. Filament fields use dot notation too (`TextInput::make('socials.github_url')`) and inside a `Repeater` item, `$get('name')` is relative to the item; `$get('../client_id')` walks up; `$get('')` returns the whole item array.

pyview note: Phoenix's client serialises nested inputs as `user[address][city]` / `user[items][0][name]` — RJSF's `bracketNameGenerator` is the same convention; Plug's `Plug.Conn.Query.decode` is the reference decoder pyview lacks today.

## Validation & error model

**RJSF**: the validator (Ajv 8) returns `RJSFValidationError { name?: 'required'|'minLength'..., message?, params?: any, property?: '.tasks.0.title', schemaPath?: '#/properties/...', stack: '.name is a required property', title? }` (packages/utils/src/types.ts:241). These are also folded into an `ErrorSchema` — a tree mirroring the data with `__errors: string[]` leaves — which templates read per field. Three hooks: `customValidate(formData, errors, uiSchema, errorSchema)` where `errors.pass2.addError("Passwords don't match")` (runs *after* schema validation; must return `errors`); `transformErrors(errors, uiSchema)` to rewrite messages by `error.name`; `extraErrors: ErrorSchema` for async/server errors (`{candy:{bar:{__errors:['...']}}}`), display-only unless `extraErrorsBlockSubmit`. Timing: `liveValidate: 'onChange'|'onBlur'|false` (booleans deprecated), plus `onBlur(id, value)`, `focusOnFirstError` (bool or `(error: RJSFValidationError) => void`), `showErrorList: 'top'|'bottom'|false`. i18n: `translateString(TranslatableString, params)` for UI chrome; Ajv message localisation is via `ajv-i18n` (`localizer` option on `customizeValidator`).

**JSON Forms**: Ajv `ErrorObject[]`; `validationMode: 'ValidateAndShow' | 'ValidateAndHide' | 'NoValidation'` (store.ts:81); `additionalErrors?: ErrorObject[]` merged into state for server errors (must carry `instancePath`). i18n via `i18n: {locale, translate, translateError}` where `Translator = (id, defaultMessage?, values?) => string` and `ErrorTranslator = (error: ErrorObject, translate, uischema?) => string` — message keys are derived from the control path (`path.error.required`) with fallbacks. Timing is coarse: validation runs on every change; there is no per-field touched state in core (renderers show errors as soon as `ValidateAndShow`, though the material renderers' `showUnfocusedDescription`/`hideRequiredAsterisk` are ui options only).

**FormKit**: `validation="required|length:3,10|email"` parsed by `parseRules()` (packages/validation/src/validation.ts) into a rule stack; per-rule hints (`parseHints`): `*rule` = `force: true` (run even if an earlier rule failed), `+rule` = `skipEmpty: false` (run on empty value), `?rule` = `blocking: false` (warning that does not block submit), `(300)rule` = `debounce: 300` ms (for async rules like username-taken). Rules are `FormKitValidationRule = ({value, node}, ...args) => boolean | Promise<boolean>`; ~40 built-ins (`accepted, alpha, alphanumeric, between, confirm, contains_*, date_after, date_before, date_between, date_format, email, ends_with, is, length, lowercase, matches, max, min, not, number, require_one, required, starts_with, symbol, uppercase, url`, ...). Messages come from `@formkit/i18n` locales keyed by rule name, overridable per input with `:validation-messages="{ required: 'Please fill this in' }"` and `validation-label`. `validation-visibility: 'live' | 'blur' | 'dirty' | 'submit'` (props.ts:734) decides *when* messages become visible (default `blur`; `submit` for forms). Server errors: form-level `:errors="[...]"` and `:input-errors="{ 'address.city': ['...'] }"` (useInput.ts:398-425 applies them as `type:'error'` messages with `meta.source = '<name>-prop'` so they are cleared as a group; keys may be nested paths). `node.setErrors(local, childErrors)` is the imperative form (used by `@formkit/vue`'s `setErrors(formId, ...)`).

**Filament/Livewire**: Laravel's validator. Filament fields expose dedicated methods (`->required()`, `->email()`, `->minLength(3)`, `->unique(table, column, ignoreRecord: true)`, `->rules(['regex:...', new Uppercase()])`, closure rules `fn (string $attribute, $value, Closure $fail)`), all of which may be closures for conditional rules (`->required(fn (Get $get) => filled($get('company_name')))`). Custom text: `->validationAttribute('full name')`, `->validationMessages(['unique' => 'The :attribute has already been registered.'])`. Docs warn: "Some default Laravel validation rules rely on the correct attribute names and won't work when passed via rule()/rules(). Use the dedicated validation methods". Repeater has `minItems/maxItems` and `->distinct()` per child. Livewire: `#[Validate('required|min:5', message: '...', as: 'post title')]` attributes on properties; `$this->validate()` on submit; `.live`/`.blur` updates run only that property's rules server-side (`HandlesValidation::validateOnly($field, $rules, $messages, $attributes)`; if it fails "the property won't be updated on the server"); manual `$this->addError(key, msg)`, `$this->resetValidation(?key)`, `$this->getErrorBag()`. Errors are keyed by dotted path (`form.title`, `items.0.name`) and read with `@error('items.0.name')`.

## Form state (bound/unbound, touched/used, attempted values)

- RJSF: single `formData` object (controlled, or `initialFormData` for uncontrolled); no touched map in core — visibility is all-or-nothing via `liveValidate`, with `onBlur` timing as the middle ground. `errorSchema` + `extraErrors` are merged for display. Submit gives `{formData, errors, errorSchema, schema, uiSchema, status: 'submitted'}` (unverified exact key list).
- JSON Forms: redux-like core store `{data, schema, uischema, errors, validationMode, additionalErrors}`; a `Control` gets `{data, errors, visible, enabled, required, path}` props. No touched/dirty in core.
- FormKit: each node has `context.state` with `blurred`, `dirty`, `touched` (unverified: `touched` may be `dirty` only), `valid`, `validationVisible`, `submitted`, `settled`, `failing`; `dirty-behavior="compare"` compares to initial value. Form node has `disabled` on submit, `submit-attrs`, `incomplete-message`.
- Livewire/Filament: state is server-side PHP properties, hydrated every request; `wire:dirty` / `wire:dirty.class="border-yellow-500"` directives expose dirtiness; Filament tracks `$this->data` and the *dehydrated* result (`->dehydrateStateUsing(fn)`, `->dehydrated(false)`/`->saved(false)` in v4 to keep a field out of the saved payload — e.g. password confirmations).

## Rendering & customization & styling

RJSF's registry has three tiers: **Widgets** (`WidgetProps { id, name, value, onChange, onBlur, onFocus, options, schema, uiSchema, registry, rawErrors, ... }`), **Fields** (`ui:field: 'MyField'` replaces the whole node incl. children; `ui:fieldReplacesAnyOrOneOf`), and **Templates** (`FieldTemplate`, `ObjectFieldTemplate`, `ArrayFieldTemplate`, `ArrayFieldItemTemplate`, `BaseInputTemplate`, `ErrorListTemplate`, `FieldErrorTemplate`, `FieldHelpTemplate`, `TitleFieldTemplate`, `DescriptionFieldTemplate`, `WrapIfAdditionalTemplate`, `ButtonTemplates.{AddButton, RemoveButton, MoveUpButton, MoveDownButton, SubmitButton}`; 6.x adds `GridTemplate`, `MultiSchemaFieldTemplate`, `OptionalDataControlsTemplate`). Per-node styling: `ui:classNames`, `ui:style`, `ui:options.label/placeholder/help/description/hideError/inputType/rows/enumNames/enumDisabled/order`. `formContext` passes arbitrary app context to every widget/template.

```tsx
function CustomFieldTemplate(props: FieldTemplateProps) {
  const { id, classNames, style, label, help, required, description, errors, children } = props;
  return (
    <div className={classNames} style={style}>
      <label htmlFor={id}>{label}{required ? '*' : null}</label>
      {description}{children}{errors}{help}
    </div>
  );
}
<Form schema={schema} validator={validator} templates={{ FieldTemplate: CustomFieldTemplate }} />
```

JSON Forms: `renderers={[...materialRenderers, { tester: rankWith(3, scopeEndsWith('rating')), renderer: RatingControl }]}` — the *tester* is the customisation API; `withJsonFormsControlProps(MyControl)` injects `{data, handleChange, path, errors, label, visible, enabled, uischema, schema}`. Renderer sets: `@jsonforms/material-renderers`, `vanilla-renderers` (class-name based, `JsonFormsStyleContext` maps style ids -> classes), `angular-material`, `vue-vuetify`, `vue-vanilla`.

```ts
export const materialTextControlTester: RankedTester = rankWith(1, isStringControl);
export const materialEnumControlTester: RankedTester = rankWith(2, isEnumControl);  // beats text for enum strings
```

FormKit: three ways, from cheap to total: (a) classes — `:classes="{ outer: 'mb-4', input: '$reset border' }"` or global `config.rootClasses` / `@formkit/themes` `generateClasses({ text: { outer: '...', input: '...' } })` (Tailwind plugin `@formkit/tailwindcss`); (b) slots per section (`<template #label="{ label }">`), plus `prefix/suffix` sections and `sections-schema` prop to rewrite a section's schema; (c) `createInput(schemaOrComponent, {props, features})` to define a new input type registered in `defaultConfig({inputs:{...}})`. Every section renders with `data-type`, `data-invalid`, `data-disabled`, `data-complete` attributes (outer.ts) so pure-CSS theming is possible.

Filament: `->label()`, `->helperText()`, `->hint()`, `->hintIcon()`, `->placeholder()`, `->inlineLabel()`, `->columnSpan()`, `->extraAttributes(['class' => '...'])`, `->extraInputAttributes()`, `->extraFieldWrapperAttributes()`, and in v4 slot-like `->aboveLabel()/->belowContent()/->afterLabel()` etc. (a whole section of "Adding extra content ... above/below/before/after label/content/error message"). Custom fields are Blade views (`->view('forms.components.my-field')`) wrapping `<x-dynamic-component :component="$getFieldWrapperView()" :field="$field">` with `x-data` Alpine and `$applyStateBindingModifiers('wire:model')`. Layout is first-class: `Section`, `Grid`, `Fieldset`, `Tabs`, `Wizard::make([Step::make('Order')->schema([...])])`, `->columns(2)`.

Livewire delegates markup entirely to Blade; recommended pattern is extracting `<x-input wire:model="title" />` Blade components with `@error` inside; custom controls via `wire:model` on a component using `$wire.entangle`/`x-modelable` (v4 doc section "Custom form controls").

## Nested / dynamic / conditional

- **RJSF**: `dependencies` (property and schema deps; "dynamic" form uses a restricted `oneOf` keyed on the trigger's `enum`, see dependencies.md:104), `oneOf`/`anyOf` (rendered by `MultiSchemaField` with a selector widget; `ui:options` can be per-branch via `oneOf: [{...}]` in uiSchema), `if/then/else` (supported via Ajv + `retrieveSchema`, resolves at render), `additionalProperties` (key/value editing with `WrapIfAdditionalTemplate`, `duplicateKeySuffixSeparator`), arrays with `ui:options.orderable/addable/removable/copyable` and per-item `items` uiSchema (6.x "Dynamic UI Schema Examples"). Caveat: when a branch changes, stale data lingers unless `omitExtraData`.
- **JSON Forms**: `rule: { effect: 'SHOW'|'HIDE'|'ENABLE'|'DISABLE'|'READONLY'|'WRITABLE', condition: { scope: '#/properties/dead', schema: { const: true }, failWhenUndefined?: true } }`, or `LeafCondition {scope, expectedValue}`, `ComposableCondition {type:'AND'|'OR', conditions}`, and (3.x) a `validate(context)` function condition. Hidden data is *not* removed from `data` by default. Nested objects render via `isObjectControl` (a Group) and `detail` option (`options.detail: 'GENERATED' | 'DEFAULT' | <uischema>`) for array items.
- **FormKit**: Vue conditionals in templates, or in `FormKitSchema`: `{ $formkit: 'text', name: 'other', if: '$get(reason).value === "other"' }`, `{ $el: 'ul', for: ['item', 'index', '$items'], children: [...] }`; `$get(id)` reads any node by `id`. `type="list"` + `dynamic` for computed lists; `@formkit/addons` `repeater` with `min/max`, `add-label`, `#controls` slot (unverified detailed prop names).
- **Filament**: `->live()` + closures is the whole model: `TextInput::make('company_name')->hidden(fn (Get $get): bool => ! $get('is_company'))`; `Select::make('state')->options(fn (Get $get) => State::where('country', $get('country'))->pluck(...))`; `->afterStateUpdated(fn (Set $set, ?string $state) => $set('slug', Str::slug($state)))`. Repeater: `->schema([...])->addable(false)->deletable(false)->reorderable(false)->reorderableWithButtons()->collapsible()->cloneable()->minItems(1)->maxItems(5)->itemLabel(fn (array $state): ?string => $state['name'] ?? null)->defaultItems(1)->simple(TextInput::make('email'))->table([...])`. Builder: `Builder::make('content')->blocks([Block::make('heading')->schema([...]), Block::make('paragraph')->schema([...])])` for heterogeneous (tagged-union) lists — the direct analogue of a Pydantic discriminated union list. `Wizard::make([Step::make('Order')->schema([...])->afterValidation(fn)])` validates per step. Nested repeater `$get('../../x')` path syntax.
- **Livewire**: arrays of arrays in properties; loops need `wire:key="{{ $item['id'] }}"` on repeated roots or the DOM diff (morph) misattributes inputs — the same reason Phoenix needs `phx-key`/ids.

## Pain points & criticisms

- RJSF: uiSchema must mirror the data tree, so deep/array uiSchemas become verbose; layout needs the 6.x `LayoutGridField` or a custom `ObjectFieldTemplate`; `oneOf` selection UX is generic and leaves stale data (`omitExtraData`/`liveOmit` exist precisely because of this); `experimental_defaultFormStateBehavior` has six sub-options — evidence that "defaults vs data" is genuinely hard; Ajv error messages are developer-facing until `transformErrors`/`ajv-i18n`; any custom Field must re-implement children rendering via `SchemaField` from `registry.fields`.
- JSON Forms: two documents to keep in sync (schema + uischema), scopes are JSON pointers into the *schema* (`#/properties/a/properties/b`) which are brittle on refactor; no per-field touched state in core; rule conditions are limited to JSON Schema `const`/`enum` tests unless you use the (3.x) function condition, which breaks serialisability; the vanilla renderers are unstyled and the material set is opinionated.
- FormKit: the string rule DSL is untyped (typos fail at runtime), Vue-only, and the sections/`rootClasses` system has a learning curve; theming Tailwind requires a build plugin; `FormKitSchema` expressions are a mini-language.
- Filament: tightly bound to Laravel/Livewire/Alpine; every `->live()` field costs a round trip and a full schema re-render (v4 added `partiallyRender*` / `*Js()` escape hatches to mitigate); state is an untyped `$data` array (typed `$get->string()` added in v4 as a patch); reactivity closures referencing other fields are stringly typed (`$get('company_name')`); custom fields require Blade + Alpine.
- Livewire: DOM morphing needs `wire:key`; nested arrays bound to inputs are stringly paths; validation messages are Laravel's, error keys are dotted paths that differ from HTML `name`s.
- Generic to schema-driven forms (all four): they excel at CRUD/admin (Filament's own positioning) and fail at marketing/bespoke flows; the "escape hatch cliff" — once one field needs custom markup, users often eject the whole form.

## Lessons for pyview — steal / adapt / avoid

**Steal**
1. The four-layer split as *explicit* Python objects: `FormSchema` derived from the Pydantic model (types, constraints, discriminators, nested/list shape) -> `UiSchema`/field options overlay (widget, label, order, help, visibility) -> `WidgetRegistry` resolving `(field_info, ui_options) -> widget` by tester/rank (JSON Forms style: `rank_with(2, is_enum)` beats `rank_with(1, is_str)`) -> `Theme` = a registry of *templates* (t-string or Ibis) for `field_wrapper`, `label`, `errors`, `help`, `array_item`, `object`, `buttons` plus a `classes` map keyed by section name (FormKit style `outer/wrapper/label/inner/input/help/messages/message`). A "theme" is then just a dict merged over defaults, exactly like `withTheme({...})`.
2. Path-derived ids and names with pluggable generators: `name="user[address][city]"`, `id="user_address_city"`, and a `decode_nested(parse_qs(...))` step (Plug.Conn.Query semantics) as the *first* thing in the pipeline; the error tree keyed by the same path tuples (`('address','city')`) so `errors_for(path)` and `input_name(path)` are inverses.
3. FormKit's *when-to-show* knob as a first-class config: `validation_visibility: 'live' | 'blur' | 'dirty' | 'submit'` per field and per form, implemented on top of Phoenix `_target` (touched set) and `phx-blur`; plus per-rule hints `blocking=False` (warnings) and debounce for async checks — mapped onto `phx-debounce`.
4. Filament's closure-with-injected-parameters style for conditional rules/visibility, using pyview's existing signature-driven binding: `Field(visible=lambda get: get('is_company'))`, `required=lambda get: bool(get('company_name'))`, with `get` supporting relative paths inside list items (`'../client_id'`). This is the "deeply nested + conditional" requirement without a second schema language.
5. Server-error merge by path, display-only by default (RJSF `extraErrors`, FormKit `input-errors`, Livewire `addError`): `changeset.add_error(('address','city'), 'Unknown city', code='not_found')` that does not get wiped by the next Pydantic validation unless the field changes (FormKit's `meta.source` grouping is the right mechanism).
6. Discriminated-union lists rendered like Filament's `Builder` blocks (Pydantic `Annotated[Union[A, B], Field(discriminator='kind')]` -> a block picker + per-block sub-schema); repeater ops as events (`add_item(path)`, `remove_item(path, idx)`, `move_item`) with stable item keys for `phx-key`/ids.

**Adapt**
- Pydantic `ValidationError.errors()` already gives `{type, loc, msg, input, ctx}` — that is RJSF's `{name, property, message, params}` and JSON Forms' Ajv `ErrorObject`; keep `type` as the i18n key and `ctx` as params, and render messages through a translate hook `(code, params, default) -> str` like JSON Forms' `ErrorTranslator`.
- Filament's dedicated rule methods over raw rule strings ("use the dedicated validation methods whenever you can") suggests: prefer Pydantic `Field(min_length=3)`/`Annotated` constraints over a FormKit-style string DSL; if a string DSL is offered, keep it tiny and typed.
- Live re-render cost: Filament's `live()` defaults to *not* re-rendering; pyview should validate per `_target` (Livewire `validateOnly`) and only re-diff the affected subtree.

**Avoid**
- A second JSON "uiSchema" document mirroring the data tree (RJSF) or JSON-pointer scopes (JSON Forms): in Python the overlay should be `Annotated[str, Ui(widget='textarea')]` / `model_config` / a `Form.Meta`-style class, or a fluent builder over the model, not a parallel dict to keep in sync.
- Untyped `$data`-array state (Filament v3) — keep the Pydantic instance (or partial `model_construct`) as the source of truth and expose typed accessors in templates.
- Requiring users to reimplement children when they customise one node (RJSF custom Field): make the *wrapper* templates (label/errors/help) and the *widget* independently replaceable, and give every widget a default that can be wrapped, not only replaced (RJSF's "Wrapping BaseInputTemplate" pattern).
- Hidden-but-still-submitted data (JSON Forms `HIDE`, RJSF stale `oneOf` data): when a field is hidden by a rule, drop it from the changeset (`dehydrated(False)` semantics) and from validation.
