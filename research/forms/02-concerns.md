# Part 2 — The concerns a form system has to separate

"It feels like there are a few different concerns" is exactly right; the libraries that age well are the ones that keep these apart. Fourteen concerns show up in every ecosystem we looked at. For each: what it is, the design axis, and who does it best.

| # | Concern | The question | Axis | Reference implementations |
|---|---|---|---|---|
| 1 | **Wire decoding** | How do flat `name=value` pairs become a nested structure? | naming grammar (`a[b][0][c]` vs `a.b[0].c` vs `a-0-c`), sparse indices, repeated keys, limits | Plug.Conn.Query / Rack (brackets), Conform (`todos[0].content`), ASP.NET (`Items[0].Name` + `.index`), Django/WTForms (flat prefixes — the weak spot) |
| 2 | **Schema & introspection** | Where do field names, types, defaults, constraints, nesting come from? | model-derived vs declared form class vs JSON schema vs combinators | Django ModelForm, AshPhoenix auto forms, superforms adapters, RJSF (JSON Schema), formlets (applicative shape) — **pydantic gives us this for free** |
| 3 | **Coercion** | How do strings become typed values, and what does `""` mean? | input-source-specific rules (dry-schema `Params` vs `JSON`), empty-value policy, checkbox/absent semantics | Ecto `cast` + `empty_values`, Conform `coerceFormValue`, dry-schema Params, ActiveModel::Type |
| 4 | **Validation** | Field rules, cross-field rules, async/server rules, when each runs | schema-vs-rules split, "rules only when schema passes", validation groups/steps | dry-validation, Ecto validations vs constraints, Bean Validation groups, FluentValidation `When`, Conform server-only validation |
| 5 | **Error model** | What is an error, how is it addressed, what is code vs message? | `(path, code, params)` vs strings; nested trees vs flat maps; form-level errors | Ecto `{msg, opts}`, Rails `errors.details`, Django `ValidationError(code, params)`, Standard Schema issues, Rust `validator` — pydantic's `loc/type/ctx` is already this |
| 6 | **Messages & i18n** | How does a code become a sentence a human wants to read, in their language? | catalog + interpolation + lookup hierarchy (app → model → field → code), plurals, labels | Rails i18n chain, Laravel `validation.php` + `attributes`, Spring message codes, Gettext in Phoenix, GOV.UK content rules |
| 7 | **Form state** | Bound/unbound, touched/used/dirty, submitted, attempted values, reset | client vs server ownership; what gates error display | Ecto `action`, LiveView `used_input?`/`_unused_`, Conform `touchedFields`, RHF `touchedFields`/`mode`, ASP.NET `ModelState.AttemptedValue`, Blazor `EditContext.IsModified` |
| 8 | **Identity** | How are inputs named and id'd, and how do list rows keep identity across re-renders? | index-based names + stable keys for ids; persistent ids | LiveView `_persistent_id`, RHF `field.id`, Conform `key`, Django `auto_id` |
| 9 | **Rendering** | Who emits HTML: the library, helpers, or the user? | layers: auto-render → field helper → attribute helper → raw HTML | Phoenix `<.input>` + `FormField`, Conform `getInputProps` ("helpers are optional"), Django `BoundField` + templates, simple_form |
| 10 | **Widgets & inference** | Which control for which type, and how to swap one? | type → widget map, registry, tester/rank dispatch, per-field override | Django `Widget`, RJSF `ui:widget` + registry, JSON Forms testers, simple_form input types, `phx.gen.html` inputs |
| 11 | **Layout & UI hints** | Order, groups, placeholders, help text, conditional visibility hints | in-model metadata vs side-car UI schema vs template | RJSF `uiSchema`, Filament fluent schema, FormKit schema, `Field(title, description)` |
| 12 | **Styling / theming** | How do classes and markup change without forking the library? | class maps, wrapper DSL, template packs, copy-the-component | FormKit `rootClasses`/sections, simple_form wrappers, DRF/crispy template packs, Phoenix generated `core_components` |
| 13 | **Dynamic structure** | Add/remove/reorder rows, conditional subforms, dependent fields, wizards | server-driven intents vs client state; discriminated unions | Ecto `sort_param`/`drop_param` + `inputs_for`, Conform intents, AshPhoenix `add_form`, Filament Repeater/Builder, Django formsets (anti-pattern) |
| 14 | **Cross-cutting** | Uploads, CSRF, mass-assignment, limits, a11y, testing, debugging | — | LiveView uploads, Rails strong params / Ecto `cast` permitted list, GOV.UK error summary, superforms `SuperDebug`, `Phoenix.LiveViewTest.form/3` |

Three observations that drive the proposal in Part 4:

1. **Concerns 1, 3, 5, 7, 8 are protocol, not preference.** They must be decided once, centrally, and match the Phoenix client. Getting them wrong (flat `parse_qs`, first-`loc`-element errors, "touched = key in changes") is what makes the current `ChangeSet` hard to grow.
2. **Concerns 2 and 4 are already solved by pydantic**, and better than most form libraries solve them (typed, nested, unions, `loc` paths). The job is to *not* duplicate them, and to fill the two gaps pydantic has for forms: empty-string coercion and server-side checks.
3. **Concerns 9–12 are where "customizable" lives**, and the winning pattern is identical across Phoenix, Conform, Django 4+, FormKit and simple_form: a small computed *field object* is the contract; helpers are thin functions over it; markup and classes are replaceable per widget; the user can always drop to raw HTML with only names/ids/values. Any design that couples rendering to validation (WTForms widgets on fields, RJSF's generic UI) ends up fought against.
