# Part 3 — The landscape: what each library taught us

Each digest ends with **take** (ideas adopted in Part 4) and **leave** (ideas deliberately not copied). The full write-ups, with code and sources, are in `appendix/`.

## 3.1 Archetypes

- **Model-derived forms** — Django `ModelForm`, Rails `form_with model:` + simple_form, AshPhoenix auto forms, WTForms-SQLAlchemy `model_form`, admin generators (sqladmin, starlette-admin, flask-admin). *"Here's my model, do the rest."* Great golden path; customisation is where they differ.
- **Declared form classes** — Django `Form`, WTForms, Deform/Colander, Play Forms mappings. A second schema next to the domain model; explicit, but duplicated.
- **Changeset / submission pipelines** — Ecto changesets, Conform submissions, dry-validation contracts, Reform. Data-in, typed-out, errors-as-data, explicit actions; rendering left to a separate layer.
- **Schema + UI-schema generators** — RJSF, JSON Forms, Formily, FormKit schema, Filament's fluent schema. Maximal auto-render, layered customisation, risk of "generic look" and config sprawl.
- **Client state libraries** — React Hook Form, TanStack Form, Formik, Angular Reactive Forms, VeeValidate. Rich touched/dirty/valid state and validation timing; not directly applicable to a server-driven framework but the *semantics* are.
- **Functional formlets** — digestive-functors, yesod-form, elm-form, composable-form. Naming + rendering + parsing as one composable value; the applicative "static shape" is exactly what a pydantic model provides.

pyview sits at the intersection of the first and third archetype: a pydantic model *is* the schema, so the form object only needs the changeset's state model and a rendering layer that is optional.

## 3.2 Ecto.Changeset (Elixir)

A changeset is a pure data structure — `data`, `params`, `changes`, `errors`, `valid?`, `action` — built by a pipeline of plain functions (`cast |> validate_required |> validate_length |> cast_embed |> unique_constraint`). Nothing in it knows HTML. `cast/4` filters permitted keys, casts types and normalises empty values (`""` → `nil`); validations run only on non-nil changes; errors are `{field, {"template with %{count}", [count: 3, validation: :length]}}` and are translated late (Gettext). Error *display* is gated by `action`: `nil` after mount means "no errors yet". Nested data goes through `cast_embed/cast_assoc`, which match children by primary key, accept index-keyed maps, and since 3.10 support `sort_param`/`drop_param` so add/remove/reorder needs no JS. Constraints map database errors back to fields after the fact.

**Take:** the three buckets (data/params/changes) and value precedence changes → params → data; the `action` gate; errors as (template, params) translated at render; `empty_values`; `sort/drop` semantics for rows; constraints-as-post-hoc-errors; schemaless changesets for non-DB forms. **Leave:** persistence concerns (`repo`, `prepare`) inside the struct; `on_replace: :raise`; the polymorphic `field.value`; two shapes for nested errors; magic param suffixes the user must type by hand.

## 3.3 Phoenix LiveView forms (server) and the JS client

Three layers in three libraries: `Phoenix.HTML.FormData` protocol + `%Form{}`/`%FormField{id, name, value, errors}`, the changeset adapter in `phoenix_ecto` (incl. `input_validations` → `required/minlength/max/step`), and `<.form>`/`<.inputs_for>`/`to_form` in LiveView. Widgets (`<.input>`) are *generated into the app* so styling is never a library concern. `inputs_for` injects a hidden `_persistent_id` per row so DOM ids stay stable across reorders. Error visibility = `action` set **and** input used; "used" moved from the 0.20 client-side `phx-feedback-for`/`phx-no-feedback` CSS trick to server-side `used_input?` reading `_unused_<name>` params in 1.0.

The client (verified in the 0.20.17 source) sends `new FormData(form)` as a urlencoded string with names verbatim; in 0.20.17 `_target` and `phx-value-*` are appended into that string (1.0.6+ moves them to a `meta` key); a `<button name=… value=…>` that dispatches a `change` event is treated as the submitter and its pair is included — the whole mechanism behind zero-JS add/remove rows. Debounce flushes on blur and submit; the focused input is never value-patched; a `phx-change` form without `phx-submit` becomes a native HTTP submit; recovery replays a `phx-change` after reconnect.

**Take:** the `FormField` triple as the template contract; escape hatches at every layer; persistent row ids; the used+action double gate implemented server-side; bracket names and `_target` paths; `phx-debounce="blur"` defaults; `JS.dispatch("change")` buttons; recovery. **Leave:** the CSS feedback mechanism (deprecated upstream); `_unused_` keys leaking into params; five-piece hand-written sort/drop markup; `:let={f}` vs `@form` duality.

## 3.4 Conform (Remix/React)

Progressive-enhancement first: the `<form>` is the source of truth, the library keeps only metadata (errors, touched fields, list keys, constraints). One path grammar (`address.city`, `todos[0].content`, `tags[]`) keys names, errors, constraints and ids. Every non-submit interaction is an **intent** (`validate`, `insert`, `remove`, `reorder`, `update`, `reset`) sent as a normal submission via a hidden `__intent__` button, applied to the payload *before* validation on both client and server. `parseWithZod` returns a `Submission` with `status` (`success` / `error` / `undefined` = "was an intent"), `payload`, `value` or `error`, and `reply()`; coercion is schema-driven (`""` → undefined, `"on"` → true, scalar → `[scalar]`, missing object → `{}` so leaf errors appear); HTML constraints are derived from the schema; validation timing is `shouldValidate`/`shouldRevalidate` (`onBlur` then `onInput` is the documented sweet spot).

**Take:** intents as the list-mutation protocol; the submission/reply shape; schema-driven coercion table and constraint derivation; errors keyed by the same paths as names; touched semantics with prefix matching; `getInputProps`-style attribute helpers with a11y wiring; "helpers are optional". **Leave:** DOM-as-only-truth (conditional fields lose values); the key/remount dance; JSON-in-a-button as the primary channel; two coexisting API generations.

## 3.5 Django Forms and WTForms

Both are declarative form classes whose attributes are Field objects (validate + coerce) owning a Widget (render; in Django also `value_from_datadict`). Django adds `BoundField` — the glue object templates use (`html_name`, `id_for_label`, `errors`, `value()`, `css_classes`, `as_widget(attrs)`) — and moved rendering to templates in 4.0/5.0 precisely because string-built `as_p`/`as_table` could not be styled; crispy-forms, widget-tweaks and django-formset exist to fill the gap. Errors are `ValidationError(message, code, params)` with per-field `error_messages` overrides and lazy translation. Data flow is flat and stringly (`QueryDict`, `pets-0-name`); nested lists are formsets with a `ManagementForm` and `__prefix__` cloning, and WTForms `FieldList(FormField)` with index-in-name — the weak spot of both. `ModelForm` / `model_form` are the closest thing to "here's my class".

**Take:** the Field/Widget/BoundField split mapped onto pydantic (pydantic is the Field layer; we add the other two); `field_flags`/`widget_attrs` → HTML attribute sync; `errors.as_data()`-style structured errors with a merged message table; two-phase validation and `add_error`; template packs/renderers as the styling layer; `empty_permitted` for untouched optional sub-forms. **Leave:** management forms and `__prefix__` cloning; flat `cleaned_data` dicts; codeless error strings; `DataRequired` rejecting `0`/`False`; mutating `self.fields` in `__init__` as the conditional-form story.

## 3.6 Superforms, Formsnap, React Hook Form, TanStack Form, Formik, Zod/Valibot/Standard Schema

The client-state libraries have converged on the same state model: **errors mirror the data shape** (`errors.address.city`, `errors.items[0].name`, plus a `_errors`/`root` slot at every node for object-, array- and form-level errors); **touched/tainted/dirty mirror the data shape** and gate error display; validation timing is a policy (`onTouched`/`auto` = "reward early, validate late": show on blur, then re-validate live once a field has an error; everything after submit); list rows carry a stable `id`/`key`; multiple forms are keyed by id; and debug tooling (`SuperDebug`, RHF DevTools) is treated as a feature. Superforms adds a schema-adapter layer (zod/valibot/arktype/… via JSON Schema) from which it derives HTML **constraints** (`required minlength maxlength min max step pattern`) that users spread onto inputs, and does schema-driven coercion of posted strings — but refuses nested objects in urlencoded mode (`dataType: 'json'` required), its most-cited limitation. Zod v4's `treeifyError` and the Standard Schema `issues[{message, path}]` shape are the emerging cross-library error format.

**Take:** errors and used-state addressed by data paths with node-level slots; constraint derivation from the schema; the `auto` timing policy; stable row ids; a debug panel; form-level/server error slots that survive re-validation (namespace external errors). **Leave:** JSON-mode nesting; silent coercion that swallows invalid input; dot-only *or* bracket-only path syntax (accept both on the Python side, emit brackets on the wire).

## 3.7 Schema-driven UI generators and fluent builders: RJSF, JSON Forms, FormKit, Filament, Livewire

All four converge on a **four-layer split**: data schema (types, constraints) → UI schema (widget, order, layout, visibility rules) → widget/renderer registry (looked up by name or by tester rank, `rankWith(2, isEnum)` beating `rankWith(1, isString)`) → theme (wrapper templates + class maps per section: `outer/wrapper/label/inner/input/help/messages`). RJSF derives ids from paths (`root_tasks_0_title`) and can emit bracket names (`root[tasks][0][title]`) — the shape Phoenix already sends. JSON Forms' `rule: {effect: SHOW|HIDE|ENABLE|DISABLE, condition}` is the cleanest declarative conditional; FormKit's `validation-visibility: live|blur|dirty|submit` is the best ergonomic knob for *when* errors show, and its `errors`/`input-errors` props merge server errors by path. Filament's fluent DSL with injected closure parameters (`->hidden(fn (Get $get) => !$get('is_company'))`, `Repeater`, `Builder` for tagged blocks) is the most "here's my model, do the rest" DX; Livewire binds nested state with `wire:model="items.0.name"` and validates per property on `.live`/`.blur` round-trips. Where they fall down: layout, bespoke UX, the generic look, and the "escape-hatch cliff" (one custom field and you abandon the generator).

**Take:** the four explicit layers with pydantic as layer 1; tester/rank widget resolution; per-field `visibility`/timing knob; closure-based conditional rules using pyview's signature binding; server-error merge by path that survives re-validation; discriminated-union lists rendered as block pickers; wrapper templates replaceable independently of widgets ("wrap, don't replace"). **Leave:** a parallel JSON uiSchema document (use `Annotated` metadata / model config instead); untyped state arrays; hidden-but-still-submitted data (drop rule-hidden fields from validation); a string rule DSL.

## 3.8 Rails, ActiveModel, simple_form, and Ruby's dry-schema / dry-validation / Reform / superform

Rails hangs its whole form stack on one naming convention (`user[addresses_attributes][0][city]`, decoded by `Rack::Utils.parse_nested_query`: `a[]` → array, `a[b]` → hash, `a[0][b]` → a hash keyed by the *string* `"0"`). Errors are typed objects (`errors.add(:name, :too_short, count: 3)` → `.details`, `.messages`, `.full_messages`, `.where`, `:base`) whose text is resolved lazily through a documented i18n chain (model/attribute/type → model/type → global type) with `%{count}` interpolation. Rails' own helpers do not infer `required`; simple_form does (`required_by_validators?`), plus `maxlength`/`min`/`max`/`pattern` from validators and input types from column type + attribute-name regexes, and its **wrappers DSL** (`b.use :label; b.use :input; b.use :error`) is the cleanest theming layer in the survey. dry-schema separates *input-source coercion* (`Params`: `""` → nil, `"1"` → true) from type/predicate checks and returns nested errors plus a typed `to_h`; dry-validation runs `rule(:field)` blocks only when the field's schema checks passed (which is exactly pydantic's after-validator rule). Reform sits between params and model with populators for nested creation; superform derives names, ids *and* the permitted-params whitelist from one form tree.

**Take:** typed error objects with a lookup chain; validator-derived HTML attributes and type inference; the wrapper pipeline as the theme contract; input-source-specific coercion before the strict layer; schema-then-rules ordering; one tree deriving names, ids and permitted keys. **Leave:** lossy silent casts; global `field_error_proc` DOM wrapping; dotted error keys that lose indices; hidden-input sentinels as user-facing API.

## 3.9 Python's pydantic-adjacent landscape: FastUI, streamlit-pydantic, FastAPI form models, FastHTML, admin generators, marshmallow, Colander/Deform, DRF

Nobody in Python has solved "here is my pydantic class, do the rest" for *nested* HTML forms. FastUI is closest (JSON schema → fields, `unflatten()` → `model_validate`, errors returned by `loc`) but raises `NotImplementedError` for variable-length lists and non-optional unions; FastAPI's `Annotated[Model, Form()]` is flat by construction (nested keys are silently dropped — verified); FastHTML binds dataclasses from flat form data; the admin generators (sqladmin, flask-admin, starlette-admin) still derive forms from ORM metadata and discover list rows from submitted key indices. Three incompatible nesting encodings coexist (dotted `items.0.qty`, DRF's `items[0]qty`, Deform/peppercorn's `__start__`/`__end__` markers) and none is Phoenix's bracket form. Error models converge on "errors keyed by path" (marshmallow nested dicts, Colander dotted keys, pydantic `loc`). Customisation patterns that work: DRF's per-field `style` dict + template packs, marshmallow's per-field `error_messages`, sqladmin's `form_args`/`form_overrides`/`form_widget_args`, FastUI's `Annotated[str, Textarea(rows=5)]` hints, marshmallow's `partial=` for progressive validation, streamlit-pydantic's discriminator-select for unions.

**Take:** `loc_to_name`/`name_to_loc` as the single source of truth; annotation-based UI hints; `partial`-style reporting (validate everything, report used paths); per-field style dicts merged over defaults; server-side add/remove on the raw params tree. **Leave:** flat extraction with silent drops; last-value-wins; order-based encodings; coupling fields to the request.

## 3.10 Pydantic v2 as the validation engine

Pydantic already emits a path-addressed error list (`type`, `loc`, `msg`, `input`, `ctx`) that walks nested models, list indices and discriminated-union branches; there are 104 built-in error types (the appendix tabulates them with templates and `ctx` keys) — the key space for messages and i18n. Lax mode is almost form-friendly (`" 21 "`, `"21.0"`, `"on"/"off"/"yes"/"no"/"1"/"0"`, ISO dates all work) except for the empty string, which fails every non-`str` type including `Optional[int]`, and scalar-for-list. Field-targeted errors from a `model_validator` work via `ValidationError.from_exception_data` and compose inside lists; after-validators do not run while field errors exist. `experimental_allow_partial` is for streaming JSON and does not help forms. Whole-model validation of a 60-field nested model costs ~15–20 µs. `model_fields` and `model_json_schema()` carry everything a renderer needs (titles, descriptions, examples, `format`, constraints). There are no async validators, and `EmailStr` needs the optional `email-validator` package.

**Take:** the error record verbatim; `loc` tuples as the universal path; the `from_exception_data` helper; `FieldInfo` + JSON-schema `format` for widgets; discriminated unions as the conditional primitive. **Leave:** `model_validate_strings`, partial validation and the pipeline API for this purpose; `info.data` cross-field rules as the *only* idiom; expecting async checks inside pydantic.

## 3.11 Error messages and i18n across ecosystems

Every mature library separates code + params from message and translates late (Ecto `{msg, opts}`, Rails `details`, Django `ValidationError(code, params)`, Rust `ValidationError{code, params}`, Zod v4 issues, FluentValidation placeholders); the message-only libraries are the ones whose docs devote pages to i18n workarounds. Labels are the hard part of good messages: GOV.UK requires wording from the question label ("Enter your first name"), Rails and Laravel inject `%{attribute}`/`:attribute`, Django deliberately omits it. Plurals belong to gettext (`ngettext`/`dngettext`), not the catalog. Override precedence is a most-specific-first chain everywhere (Spring `code.object.field → code.field → code`, Rails model/attribute/type → …, Laravel `custom.attribute.rule`), and path-based libraries strip list indices when *looking up* messages but keep them when *addressing* fields. pydantic-i18n regex-translates English strings — a hack a `type → template` catalog makes unnecessary because `ctx` gives the params natively.

**Take:** a normalised record with `{label}` as a guaranteed template parameter; a GOV.UK-voice default catalog keyed by verified pydantic types; the field.code → Model.code → code chain with indices stripped; gettext plurals via `(singular, plural, count_key)` entries; an extractable `errors.pot`; form-level errors under path `()`. **Leave:** message-only dicts; label-free defaults; runtime "attribute + message" concatenation; expression languages in templates; pydantic's `msg` as user-facing text.

## 3.12 Nested, dynamic and conditional forms across libraries

Every server-side library ends up with the same wire shape — index-named inputs plus a handful of control params in the same form (`emails_sort[]`/`emails_drop[]`, `TOTAL_FORMS`, `_destroy`, `__intent__`, `_union_type`, AshPhoenix's `_add_x`/`_drop_x[]`) — and every client library converges on stable per-row keys that are not the index. In pyview's client, verified in the bundled `app.js`, `phx-click` never carries form values; only `phx-change` and `phx-submit` serialise the form, and a named `<button>` dispatching `change` is treated as the submitter. Conditional forms are best expressed as pydantic discriminated unions (pydantic already yields `('party', 'business', 'vat')` locs and `union_tag_invalid`), keeping the unselected variant's params so switching back restores them. Dependent selects need no rules engine (`_target` says what changed). For wizards the write-up recommends one model per step composed at the end; whole-model step gating is the simpler alternative when one model fits.

**Take:** the Phoenix mechanism verbatim, generated by helpers; `_persistent_id`-style row ids; "an intent is not a submit"; `min/max_length` seeding rows and capping buttons; both wizard styles documented. **Leave:** plain `phx-click` + socket-held params as the default (lost keystrokes); a `name="_intent"` submit button placed *before* the real submit (Enter-key implicit submission adds rows); index-keyed DOM ids; `__prefix__`/`TOTAL_FORMS` client templates.

## 3.13 Form UX, error presentation and accessibility

The accessible baseline is two-level: an **error summary** at the top (`role="alert"`, heading, one link per error to the field's `id`, focus moved there on submit) *plus* an inline message per field with the same wording, a visually hidden "Error:" prefix, and `aria-describedby="{id}-hint {id}-error"` in that order (GOV.UK's tested markup; WCAG 3.3.1/3.3.3/4.1.3). Timing research converges on "not per keystroke": inline validation *after leaving the field* reduces errors and completion time (Wroblewski/Etre 2009), premature on-change validation hurts, and GOV.UK goes further (submit only). Never disable the submit button until valid; do disable it *during* submission. Error copy: specific, instructional, reusing the label's words, no "invalid"/"please"/"oops", never clear the user's input. Mark optional fields, not required ones; avoid placeholders as labels; list rows get `fieldset`+`legend`, a polite live region for add/remove announcements, and focus moves to the new row.

**Take:** the form-group markup contract as the default renderer; the error summary component; the blur-default timing policy with `submit` and `eager` switches; label-aware messages; optional-field marking; row a11y. **Leave:** first-keystroke errors; disabled-until-valid submit; summary-only or inline-only errors; leaking validator wording or paths.

## 3.14 What developers love and hate (community sentiment)

The single most-hated thing everywhere is dynamic/nested collections (formsets, `FieldList`, `cast_assoc`/`on_replace`, `accepts_nested_attributes_for`, `useFieldArray` traps, Superforms' JSON mode, Blazor's nested-validation gap) — every ecosystem needed a plugin or a tutorial industry for it. The most-loved things are explicitness and composability with zero call-site boilerplate (Ecto pipelines, Filament's DSL, simple_form/crispy one-liners, RHF's uncontrolled model, Superforms' `SuperDebug` and schema-derived defaults, Conform's "any valid HTML form"). Styling is the perennial complaint in server-rendered stacks; schema-to-form is universally wanted and disappointing when it is the *only* path; "touched/used" was a client-vs-server fight LiveView settled server-side in 1.0; pydantic is not a form parser (empty strings, absent checkboxes, developer-grade messages, flat FastAPI form models); round-trip latency with big repeaters is the LiveView/Livewire-family pain.

**Take:** design out nested-collection pain with generated protocol; keep explicit handlers; ship a debug panel; keep hand-written HTML first-class next to auto-render; default debounce on blur; consider LiveComponents/streams for very large lists. **Leave:** CSS feedback hacks; index-keyed rows without identity; schema-only rendering; raw `parse_qs` into pydantic; JS-required nesting.

## 3.15 Wide survey: .NET, JVM, Go/Rust, functional formlets, other LiveView ports

Every mature server-side ecosystem converges on one canonical path syntax used for both binding and error addressing (`Address.City`/`Items[0].Name`, Spring `groups[0].name`, Play `homeAddress.street`, Rails/serde_qs/Phoenix brackets). Attempted values are stored separately from parsed values (ASP.NET `ModelState.AttemptedValue`, Spring `rejectedValue`, Vaadin buffered `readBean/writeBean`, elm-form's raw `Form.Model`) — re-rendering from the typed model is the classic "my invalid input vanished" bug. Errors are records `{code, message template, params, path}` (Spring `FieldError`, Keats `ValidationError`, go-playground `FieldError`, Bean Validation `ConstraintViolation`) with fallback message hierarchies (Spring's `DefaultMessageCodesResolver`, index-stripped). Form-state flags beyond "valid" are first-class (Blazor `EditContext.IsModified` + CSS class provider, AshPhoenix `submitted_once?`/`just_submitted?`/`touched_forms`, elm-form `FieldStatus`, yesod's `FormMissing | FormFailure | FormSuccess`). Dynamic lists without JS exist in AshPhoenix (`_add_x`/`_drop_x[]` handled inside `validate/3`, `add_form/remove_form` by path), .NET (`Items.index` non-sequential), Thymeleaf (`__${i}__` re-post) and Play (`@repeat`). Polymorphic sub-forms use a discriminator param (`_union_type`). The applicative formlets (digestive-functors, yesod, elm-form, Play `mapping`) prove naming + parsing + rendering derive from a static shape — which is what a pydantic class is; "parse, don't validate" means typed output or a structured error tree, never a half-validated dict.

**Take:** the codec + error tree; AshPhoenix-style params handled inside `validate`; attempted-value store; `submitted_once`/`just_submitted`/`changed` flags; message-code fallback with index stripping; renderer-as-parameter (Play `FieldConstructor`, yesod `renderBootstrap3`, Blazor `FieldCssClassProvider`); widget registry by type then hint (.NET `EditorTemplates`/`[UIHint]`); converter-before-validator. **Leave:** flat `errors[loc[0]]`; sequential-only indices; validating from the typed model on re-render; stringly rule DSLs in tags; two buffering modes.
