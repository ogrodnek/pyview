# Part 3 — The landscape: what each library taught us

Each digest ends with **take** (ideas adopted in Part 4) and **leave** (ideas deliberately not copied). The full write-ups, with code and sources, are in `appendix/`.

## 3.1 Archetypes

- **Model-derived forms** — Django `ModelForm`, Rails `form_with model:` + simple_form, AshPhoenix auto forms, WTForms-SQLAlchemy `model_form`, admin generators (sqladmin, starlette-admin, flask-admin). *"Here's my model, do the rest."* Great golden path; customisation is where they differ.
- **Declared form classes** — Django `Form`, WTForms, Deform/Colander, Play Forms mappings. A second schema next to the domain model; explicit, but duplicated.
- **Changeset / submission pipelines** — Ecto changesets, Conform submissions, dry-validation contracts, Reform. Data-in, typed-out, errors-as-data, explicit actions; rendering left to a separate layer.
- **Schema + UI-schema generators** — RJSF, JSON Forms, Formily, FormKit schema, Filament's fluent schema. Maximal auto-render, layered customisation, risk of "generic look" and config sprawl.
- **Client state libraries** — React Hook Form, TanStack Form, Formik, Angular Reactive Forms, VeeValidate. Rich touched/dirty/valid state and validation timing; not directly applicable to a server-driven framework but the *semantics* are.
- **Functional formlets** — digestive-functors, yesod-form, elm-form, composable-form. Naming + rendering + parsing as one composable value; the applicative "static shape" is exactly what a pydantic model provides.

pyview sits at the intersection of the first and third archetype: a pydantic model *is* the schema, so the form object only needs the changeset's state model and a rendering layer that is optional.

## 3.2 Ecto.Changeset (Elixir)

A changeset is a pure data structure — `data`, `params`, `changes`, `errors`, `valid?`, `action` — built by a pipeline of plain functions (`cast |> validate_required |> validate_length |> cast_embed |> unique_constraint`). Nothing in it knows HTML. `cast/4` filters permitted keys, casts types and normalises empty values (`""` → `nil`); validations run only on non-nil changes; errors are `{field, {"template with %{count}", [count: 3, validation: :length]}}` and are translated late (Gettext). Error *display* is gated by `action`: `nil` after mount means "no errors yet". Nested data goes through `cast_embed/cast_assoc`, which match children by primary key, accept index-keyed maps, and since 3.10 support `sort_param`/`drop_param` so add/remove/reorder needs no JS. Constraints map database errors back to fields after the fact.

**Take:** the three buckets (data/params/changes) and value precedence changes → params → data; the `action` gate; errors as (template, params) translated at render; `empty_values`; `sort/drop` semantics for rows; constraints-as-post-hoc-errors; schemaless changesets for non-DB forms. **Leave:** persistence concerns (`repo`, `prepare`) inside the struct; `on_replace: :raise`; the polymorphic `field.value`; two shapes for nested errors; magic param suffixes the user must type by hand.

## 3.3 Phoenix LiveView forms (server) and the JS client

Three layers in three libraries: `Phoenix.HTML.FormData` protocol + `%Form{}`/`%FormField{id, name, value, errors}`, the changeset adapter in `phoenix_ecto` (incl. `input_validations` → `required/minlength/max/step`), and `<.form>`/`<.inputs_for>`/`to_form` in LiveView. Widgets (`<.input>`) are *generated into the app* so styling is never a library concern. `inputs_for` injects a hidden `_persistent_id` per row so DOM ids stay stable across reorders. Error visibility = `action` set **and** input used; "used" moved from the 0.20 client-side `phx-feedback-for`/`phx-no-feedback` CSS trick to server-side `used_input?` reading `_unused_<name>` params in 1.0.

The client (verified in the 0.20.17 source) sends `new FormData(form)` as a urlencoded string with names verbatim; in 0.20.17 `_target` and `phx-value-*` are appended into that string (1.0.6+ moves them to a `meta` key); a `<button name=… value=…>` that dispatches a `change` event is treated as the submitter and its pair is included — the whole mechanism behind zero-JS add/remove rows. Debounce flushes on blur and submit; the focused input is never value-patched; a `phx-change` form without `phx-submit` becomes a native HTTP submit; recovery replays a `phx-change` after reconnect.

**Take:** the `FormField` triple as the template contract; escape hatches at every layer; persistent row ids; the used+action double gate implemented server-side; bracket names and `_target` paths; `phx-debounce="blur"` defaults; `JS.dispatch("change")` buttons; recovery. **Leave:** the CSS feedback mechanism (deprecated upstream); `_unused_` keys leaking into params; five-piece hand-written sort/drop markup; `:let={f}` vs `@form` duality.

## 3.4 Conform (Remix/React)

Progressive-enhancement first: the `<form>` is the source of truth, the library keeps only metadata (errors, touched fields, list keys, constraints). One path grammar (`address.city`, `todos[0].content`, `tags[]`) keys names, errors, constraints and ids. Every non-submit interaction is an **intent** (`validate`, `insert`, `remove`, `reorder`, `update`, `reset`) sent as a normal submission via a hidden `__intent__` button, applied to the payload *before* validation on both client and server. `parseWithZod` returns a `Submission` with `status` (`success` / `error` / `undefined` = "was an intent"), `payload`, `value` or `error`, and `reply()`; coercion is schema-driven (`""` → undefined, `"on"` → true, scalar → `[scalar]`, missing object → `{}` so leaf errors appear); HTML constraints are derived from the schema; validation timing is `shouldValidate`/`shouldRevalidate` (`onBlur` then `onInput` is the documented sweet spot).

**Take:** intents as the list-mutation protocol; the submission/reply shape; schema-driven coercion table and constraint derivation; errors keyed by the same paths as names; touched semantics with prefix matching; `getInputProps`-style attribute helpers with a11y wiring; "helpers are optional". **Leave:** DOM-as-only-truth (conditional fields lose values); the key/remount dance; JSON-in-a-button as the primary channel; two coexisting API generations.

## 3.5 Django Forms and WTForms

Both are declarative form classes whose attributes are Field objects (validate + coerce) owning a Widget (render; in Django also `value_from_datadict`). Django adds `BoundField` — the glue object templates use (`html_name`, `id_for_label`, `errors`, `value()`, `css_classes`, `as_widget(attrs)`) — and moved rendering to templates in 4.0/5.0 precisely because string-built `as_p`/`as_table` could not be styled; crispy-forms, widget-tweaks and django-formset exist to fill the gap. Errors are `ValidationError(message, code, params)` with per-field `error_messages` overrides and lazy translation. Data flow is flat and stringly (`QueryDict`, `pets-0-name`); nested lists are formsets with a `ManagementForm` and `__prefix__` cloning, and WTForms `FieldList(FormField)` with index-in-name — the weak spot of both. `ModelForm` / `model_form` are the closest thing to "here's my class".

**Take:** the Field/Widget/BoundField split mapped onto pydantic (pydantic is the Field layer; we add the other two); `field_flags`/`widget_attrs` → HTML attribute sync; `errors.as_data()`-style structured errors with a merged message table; two-phase validation and `add_error`; template packs/renderers as the styling layer; `empty_permitted` for untouched optional sub-forms. **Leave:** management forms and `__prefix__` cloning; flat `cleaned_data` dicts; codeless error strings; `DataRequired` rejecting `0`/`False`; mutating `self.fields` in `__init__` as the conditional-form story.

## 3.6 Superforms, Formsnap, React Hook Form, TanStack Form, Formik, Zod/Valibot/Standard Schema

The client-state libraries have converged on the same state model: **errors mirror the data shape** (`errors.address.city`, `errors.items[0].name`, plus a `_errors`/`root` slot at every node for object-, array- and form-level errors); **touched/tainted/dirty mirror the data shape** and gate error display; validation timing is a policy (`onTouched`/`auto` = "reward early, validate late": show on blur, then re-validate live once a field has an error; everything after submit); list rows carry a stable `id`/`key`; multiple forms are keyed by id; and debug tooling (`SuperDebug`, RHF DevTools) is treated as a feature. Superforms adds a schema-adapter layer (zod/valibot/arktype/… via JSON Schema) from which it derives HTML **constraints** (`required minlength maxlength min max step pattern`) that users spread onto inputs, and does schema-driven coercion of posted strings — but refuses nested objects in urlencoded mode (`dataType: 'json'` required), its most-cited limitation. Zod v4's `treeifyError` and the Standard Schema `issues[{message, path}]` shape are the emerging cross-library error format.

**Take:** errors and used-state addressed by data paths with node-level slots; constraint derivation from the schema; the `auto` timing policy; stable row ids; a debug panel; form-level/server error slots that survive re-validation (namespace external errors). **Leave:** JSON-mode nesting; silent coercion that swallows invalid input; dot-only *or* bracket-only path syntax (accept both on the Python side, emit brackets on the wire).

## 3.7 Schema-driven UI generators and fluent builders: RJSF, JSON Forms, FormKit, Filament, Livewire

All four converge on a **four-layer split**: data schema (types, constraints) → UI schema (widget, order, layout, visibility rules) → widget/renderer registry (looked up by name or by tester rank, `rankWith(2, isEnum)` beating `rankWith(1, isString)`) → theme (wrapper templates + class maps per section: `outer/wrapper/label/inner/input/help/messages`). RJSF derives ids from paths (`root_tasks_0_title`) and can emit bracket names (`root[tasks][0][title]`) — the shape Phoenix already sends. JSON Forms' `rule: {effect: SHOW|HIDE|ENABLE|DISABLE, condition}` is the cleanest declarative conditional; FormKit's `validation-visibility: live|blur|dirty|submit` is the best ergonomic knob for *when* errors show, and its `errors`/`input-errors` props merge server errors by path. Filament's fluent DSL with injected closure parameters (`->hidden(fn (Get $get) => !$get('is_company'))`, `Repeater`, `Builder` for tagged blocks) is the most "here's my model, do the rest" DX; Livewire binds nested state with `wire:model="items.0.name"` and validates per property on `.live`/`.blur` round-trips. Where they fall down: layout, bespoke UX, the generic look, and the "escape-hatch cliff" (one custom field and you abandon the generator).

**Take:** the four explicit layers with pydantic as layer 1; tester/rank widget resolution; per-field `visibility`/timing knob; closure-based conditional rules using pyview's signature binding; server-error merge by path that survives re-validation; discriminated-union lists rendered as block pickers; wrapper templates replaceable independently of widgets ("wrap, don't replace"). **Leave:** a parallel JSON uiSchema document (use `Annotated` metadata / model config instead); untyped state arrays; hidden-but-still-submitted data (drop rule-hidden fields from validation); a string rule DSL.
